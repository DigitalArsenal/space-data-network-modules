## Executive summary

1. **Both reference artifacts the owner named are real, identified, and already partially
   wired into our repo.** "The aerospace study results released by TraCSS" =
   **TraCSS's "Dataset for Conjunction Assessment Verification"** (a.k.a. the "Aerospace
   IVV Dataset"), authored by Kerstyn Auman / Timothy S. Murphy / Eric George (The
   Aerospace Corporation), published by NOAA/Office of Space Commerce **March 2026**,
   CC0-1.0. It is **not a live feed** — it's a fixed, versioned, one-time-release

   that separately. This means A2.8b's hard gate should be built on **event-set
   recall + TCA + miss-distance/geometry**, with Pc checked only loosely (order-of-
   magnitude / same-method-family) — not as a pass/fail axis, contrary to what the
   task packet implies ("Pc within documented method-difference bounds" is the right
   framing, but it should be advisory, not blocking, against TraCSS).
3. **A second important finding, unprompted:** the module repo already contains
   `scripts/fetch-tor.sh` / `fetch-socrates-gp-tor.mjs` / `fetch-tor-fast.sh` — Tor-
   circuit-rotating bulk downloaders for SOCRATES `data.php`, explicitly designed to
   **rotate around HTTP 429/503 by requesting a new Tor circuit** and retry through
   errors. This is the opposite of "polite" and cuts directly against CelesTrak's
   documented anti-abuse policy (50 HTTP errors/2h → IP firewalled). Local evidence
   (git history, empty `tests/data/socrates_gp/`, 2-file cache) suggests it was **not**

4. **This sandbox cannot reach celestrak.org** (`WebFetch` → `ECONNREFUSED`), consistent
   with the A2.1 finding ("CelesTrak also ECONNREFUSED from this env"). All SOCRATES
   specifics below come from `WebSearch` snippets of CelesTrak's own pages plus
   already-checked-in local evidence (real scraped fixtures dated 2026-03-10, one live-
   cached GP pair file). A2.8b execution must run from a host with real internet
   egress (the existing scripts assume this and already have caching/politeness
   built in — see Q4).
5. Our CA module already implements almost everything needed to consume both
   references: `screen_catalog` (5 km default threshold, matches SOCRATES),

## Q1 — SOCRATES: product, cadence, screening params, access, politeness

**Product / format.** SOCRATES ("Satellite Orbital Conjunction Reports Assessing
Threatening Encounters in Space", now "SOCRATES Plus") is CelesTrak's public conjunction
report. Two summary CSV endpoints:
- `https://celestrak.org/SOCRATES/sort-maxProb.csv` — sorted by `MAXPROB` descending
- `https://celestrak.org/SOCRATES/sort-minRange.csv` — sorted by `MINRANGE` ascending
- Additional sort options exist for `TCA` and `RELSPEED` (soonest-first / fastest-first).
- CSV fields (RFC 4180, header row): `NORAD_CAT_ID_1, OBJECT_NAME_1, DSE_1,
  NORAD_CAT_ID_2, OBJECT_NAME_2, DSE_2, MAXPROB, DILUTION, TCA_RANGE,
  TCA_RELATIVE_SPEED, TIME_IN, TCA, TIME_OUT`. (`DSE` = Days Since Epoch of the GP set
  used.) Format doc: `http://celestrak.org/SOCRATES/socrates-format.php`.
- **Per-pair GP query**: `https://celestrak.org/SOCRATES/data.php?CATNR=<id1>,<id2>&FORMAT=<json|csv|tle>`
  — this returns **the exact GP elements SOCRATES used to compute that specific event**,
  not the current catalog. This is the load-bearing fact for reference-window capture
  (see Q4) and is already correctly documented in the repo
  (`scripts/fetch-socrates-gp.mjs` header comment).

**Cadence.** SOCRATES has historically run **3x/day**, screening (per CelesTrak's own
description) all active payloads against the full public unclassified GP catalog,
7 days forward. One independent source observed the "Plus" product refreshing on a
~10–11 hour cadence "right now" — i.e., cadence is not perfectly fixed and should be
**treated as approximate/observed, not contractually guaranteed**; A2.8b should record
the wall-clock time of each captured reference window rather than assume a schedule.

**Screening parameters.**
- Screening/miss-distance threshold: **5 km** at TCA (not 1 km — an earlier "250
  conjunctions within 1 km" figure floating around the literature refers to a
  different summary statistic, not the screening threshold itself).
- Forecast window: **7 days** forward from run time.
- Propagator: **SGP4**, run inside **STK/CAT** (AGI/Ansys Systems Tool Kit's
  Conjunction Analysis Tools), currently STK 12.2 per public CelesTrak commentary.
- Catalog: full public unclassified GP set from Space-Track.org (screened set =
  active payloads as primaries vs. full catalog as secondaries, per CelesTrak's own
  description of the "Plus" screening scope change).
- Pc ("MAX_PROB"): computed via the **Alfano maximum-probability method** (AIAA-03-548,
  "Relating Position Uncertainty to Maximum Conjunction Probability" — hosted at
  `celestrak.org/SOCRATES/AIAA-03-548.pdf`), falling back to Foster/Alfano power-series
  approximations by aspect ratio when full covariance isn't usable. This is the *same
  method family* our module's default `probability_method = "ALFANO-MAXPROB"` targets
  (see Q3) — a real, exploitable point of alignment.

**Access / politeness.** CelesTrak's site-wide usage policy (`celestrak.org/usage-policy.php`,
confirmed via search since direct fetch is blocked from here, and consistent with the
already-documented A2.1 finding):
- **>50 HTTP errors (301/403/404) within a 2-hour window → IP address sent to the
  firewall** (auto-blocked).
- M2M/automated clients **must stop querying immediately on any non-200 response** and
  surface it to a human — not retry, not rotate source IP, not proxy around it.
- GP data itself only refreshes every 2 hours server-side — "no need to check more often."
- No SOCRATES-specific rate limit is separately published beyond the site-wide policy;
  treat SOCRATES `data.php`/CSV endpoints as subject to the same 50-error/2h rule.
- **Explicit anti-pattern found in our own tree that violates this**: see the
  "Risk flag" section below.

Sources: [CelesTrak: SOCRATES Plus](https://celestrak.org/SOCRATES/), [CelesTrak: SOCRATES Format Documentation](http://celestrak.org/SOCRATES/socrates-format.php), [CelesTrak: Usage Policy](http://celestrak.org/usage-policy.php), [Satellite Orbital Conjunction Reports Assessing Threatening Encounters in Space (SOCRATES)](https://celestrak.org/publications/AAS/05-124/6USR-SSW-S2.2.pdf), local: `scripts/fetch-socrates-gp.mjs`, `scripts/lib/socratesReplayHarness.mjs`, `src/cpp/tests/test_socrates.cpp` (real fixtures scraped 2026-03-10).

### Purpose and disclaimer (load-bearing for how A2.8b should treat this)

> "This test set was devised primarily to evaluate conjunction geometry at the time of
> closest approach (TCA), with an emphasis on 1) finding all the same events and 2) for
> those events, accurately computing the TCA and primary/secondary state and
> covariance... While probability of collision (Pc) metrics do exist in the answer key,
> direct comparison of Pc values requires the same method of Pc computation and is
> therefore not a key metric of this dataset."

> "This test set should not be used as a validation benchmark for operational use of a
> conjunction screening algorithm; it should only be used as a diagnostic tool for
> self-evaluation" — CSieve itself is "expected to find nearly all the events... but we
> cannot guarantee exhaustive results."

**Implication for A2.8b:** frame the TraCSS comparison as *event-recall + TCA/geometry
self-diagnostic*, not an operational certification gate. Do not fail the suite on Pc
deltas against this dataset; do fail it on missed/extra events or TCA/geometry drift
beyond the tolerances in Q5.

luni-solar, SRP — see the companion AMOS paper §6.1) or hand-crafted, and don't exist
in any real catalog; they test our module's *machinery* (maneuver ephemeris handling,
OCM usable-time bounds, hyperbolic/heliocentric edge cases) rather than *catalog
realism*. A2.8b should treat these as two separate test lanes, not blend them.

### Algorithm configuration (exact, must be replicated bit-for-bit)

1. **All-vs-all** screening of every ephemeris against every other (candidate/mitigation-
   maneuver variants of the same object designator excluded from each other, but each
   screened against everything else).
2. Only CDMs with **TCA strictly inside `2025-01-01T12:00:00Z .. 2025-01-08T12:00:00Z`**
   are valid; events whose screening-volume entry occurs at the window boundary but
   whose true TCA falls outside must **not** be reported.
3. Respect each OCM's own `USEABLE_START_TIME`/`USEABLE_STOP_TIME`.
4. **No Pc pre-filter.**
5. **OD age gate: `OD_EPOCH` must be < 14 days before 2025-01-01T12:00:00Z** (screening
   window start) — objects failing this are excluded from the answer key.
6. Two independent screening-volume configurations, run and released separately:
   - **Round 1 (recommended first): single spherical 10 km volume, default HBR 0.5 m.**
     Symmetric — if A↔B conjuncts, both A-primary and B-primary CDMs are reported.
   - **Round 2: SFSH (Space Flight Safety Handbook v1.7) rectangular volumes**, 8
     orbit-regime buckets (Table 3 below), **asymmetric** — A-within-B's-volume does not
     imply B-within-A's-volume; only the triggering direction(s) are reported.

**SFSH screening-volume table (U/V/W = Radial/In-track/Cross-track, km, half-volumes):**

| ID | U | V | W | Regime | Definition |
|---|---|---|---|---|---|
| 1 | 10 | 10 | 10 | Deep Space (Table 3) | 1300<Period<1800 min, e<0.25, incl<35° |
| 2 | 0.4 | 2 | 2 | LEO4 | 1200<Perigee≤2000 km, e<0.25 |
| 3 | 0.4 | 12 | 12 | LEO3 | 750<Perigee≤1200 km, e<0.25 |
| 4 | 0.4 | 25 | 25 | LEO2 | 500<Perigee≤750 km, e<0.25 |
| 5 | 0.4 | 44 | 51 | LEO1 | Perigee≤500 km, e<0.25 |
| 6 | 20 | 20 | 20 | Deep Space (Table 4) | Period>225 min |
| 7 | 2 | 25 | 25 | LEO/Near Earth (Table 4) | Period<225 min |
| 8 | 20 | 50 | 20 | Hyperbolic (test-only, not in real SFSH) | e≥1 |

A conjunction is reportable **only if the local minimum of miss distance falls inside
the screening volume** at that same local-minimum time — a volume-crossing near TCA
that isn't itself the local minimum, or a local minimum outside the window, must not be
reported (worked example in the guide, Table 4).

### CSieve output schema (the literal "answer key" CSV columns)

`run_id, conj_id, obj1, met_criteria1, obj2 (obj2>obj1), met_criteria2, min_range (km),
Vrel (km/s), prob (Pc via Alfano 2004 method), dilution (0/1), mdistance (Mahalanobis
distance), epoch (UTC), jdate, x1,y1,z1,vx1,vy1,vz1 (J2000, km & km/s),
local_x1,local_y1,local_z1 (obj1's UVW frame), C1_xx (obj1 UVW covariance, upper
triangular), x2..vz2 (J2000), local_x2..z2 (obj2's UVW frame), C2_xx (obj2 UVW
covariance), obj1_file, obj2_file`. NULL Pc/mdistance/dilution = non-positive-definite
or missing covariance (rare).

**Note the Pc method is "Alfano 2004"** (rectangular-object accommodation paper),
distinct from both our module's `ALFANO-MAXPROB` (AIAA-03-548, matches SOCRATES) and
our `ALFANO-2005` (Orekit's Simpson-quadrature implementation). Three different Alfano
papers, three different numeric methods — reinforces "don't gate on Pc equality."

### Companion paper — the actual source of numeric tolerances

*Validation Methodology for TraCSS Conjunction Assessment* (Auman, Murphy, George,
Kelly, Coursey [Aerospace] + Goldstein, Ruh, Hymes [SpaceX], **AMOS 2025**,
`https://amostech.com/TechnicalPapers/2025/ConjunctionRPO/Auman.pdf`) is the paper the
User's Guide cites for "suggested thresholds for differences in TCA between two
conjunction screening tools." It documents Aerospace's own validation of **SpaceX's**
CS algorithm against CSieve and is the best available empirical baseline for "what does
a passing tool actually look like." Full extraction below (Q5) — this is the single
most useful primary source found in this research pass.

Key scope note from the paper itself: **"This paper focuses on... conjunction screening
(CS) processes and excludes the validation of a probability of collision (Pc)
calculation under the assumption that... NASA CARA's PcMultiStep algorithm would be
used for computing this metric."** I.e., the authoritative validation methodology
behind both TraCSS artifacts treats **CS (event-finding + geometry) and Pc as separate
concerns**, with Pc validation explicitly out of scope for tool-to-tool comparison.

Sources: [Dataset for Conjunction Assessment Verification](https://space.commerce.gov/dataset-for-conjunction-assessment-verification/), [TraCSS Publishes "Dataset for Conjunction Assessment Verification"](https://space.commerce.gov/tracss-publishes-dataset-for-conjunction-assessment-verification/), `Conjunction_Screening_Testset_Users_Guide.pdf` (fetched directly, full text extracted above), `Auman et al., Validation Methodology for TraCSS Conjunction Assessment, AMOS 2025` (fetched directly, full text extracted below).

## Q3 — Pc methodology landscape

**What our module implements** (`src/cpp/include/conjunction/pc_method.h`, all ported
against Orekit's test vectors per the README):

| Method name in our code | Basis | Notes |
|---|---|---|
| `ALFANO-MAXPROB` (**default** for `assess`/`screen`) | Alfano AIAA-03-548 (max-Pc bound) | Same family as SOCRATES's own `MAX_PROB` |
| `FOSTER-2D` | Foster-Estes 1992, 2D Gaussian | NASA CARA's current internal default method |
| `PATERA-2001` | Patera single-integral | |
| `CHAN-1997` (alias `CHAN2008`) | Chan zeroth-order analytical | Orekit `Chan1997Test` parity |
| `ALFRIEND-1999` / `ALFRIEND-1999-MAX` | Alfriend-Akella constant-density approx. | Orekit `Alfriend1999Test`/`Alfriend1999MaxTest` parity |
| `ALFANO-2005` | Orekit `Alfano2005Test` (Simpson quadrature) | Different Alfano paper than TraCSS's "Alfano 2004" |
| `LAAS-2015` | Orekit `Laas2015Test` recurrent series w/ bounds | |

**What the two reference artifacts use:**
- **SOCRATES `MAX_PROB`**: Alfano max-probability method (AIAA-03-548) — **matches our
  default `ALFANO-MAXPROB`** in method family. Real apples-to-apples Pc comparison is
  plausible here *if* HBR/combined-radius assumptions are aligned (SOCRATES/STK falls
  back to aspect-ratio power-series approximations when full covariance isn't usable;
  our module needs a `BPlaneGeometry.combinedRadius` input either way).
- **TraCSS/CSieve `prob`**: "Alfano 2004" (rectangular-object accommodation variant) —
  does not correspond to any method we implement by name, and the User's Guide itself
  says not to compare it directly.

**NASA CARA's published position on method agreement** (from search of NASA CARA
literature, not independently re-derived here): Foster is CARA's operational default
(2D Gaussian, rectilinear short-encounter assumption); Chan is fastest but least
accurate for extreme aspect ratios; Alfano performs well because its integration steps
adapt case-by-case. Across Pc magnitudes from ~0.1 down to ~1e-7, the methods are
reported as "almost always in good agreement" when given **identical inputs** (same
covariance, same combined HBR, same B-plane geometry) — divergence in practice is
almost always attributable to differing inputs (covariance source, HBR convention,
maneuver/OD age), not the analytic method itself.

**Recommendation:** set Pc tolerance as an **order-of-magnitude band** (e.g. within a
factor of 10, matching the existing `DEFAULT_PROBABILITY_RATIO_TOLERANCE = 100` already
coded in `scripts/lib/socratesReplayHarness.mjs` — that constant is if anything looser
than what the literature would justify; consider tightening it once B-plane inputs are
verified aligned) and only against SOCRATES (method-family match). Do not gate on Pc
at all against the TraCSS/CSieve answer key, consistent with the source documents.

Sources: local `src/cpp/include/conjunction/pc_method.h`, `src/cpp/include/conjunction/conjunction_assessment.h:70`, [CelesTrak SOCRATES AIAA-03-548](https://www.celestrak.org/SOCRATES/AIAA-03-548.pdf), [NASA Robotic CARA Probability of Collision](https://ntrs.nasa.gov/api/citations/20190011726/downloads/20190011726.pdf), TraCSS User's Guide + AMOS 2025 paper (both fetched directly above).

## Q4 — Reference-window capture strategy

**SOCRATES: per-pair GP capture is the correct, already-implemented strategy — not a
full-catalog snapshot.** `data.php?CATNR=id1,id2&FORMAT=json` returns the exact GP
elements SOCRATES used for that specific reported event, independent of the current
live catalog. This sidesteps the "what catalog snapshot did SOCRATES use for this run"
problem entirely: you don't need to guess or race a full-catalog download against
SOCRATES's compute cycle — you fetch the summary CSV once (`sort-maxProb.csv` and/or
`sort-minRange.csv`), then fetch `data.php` for only the N pairs you want to check in
as fixtures. This is exactly what `scripts/fetch-socrates-gp.mjs`,
`scripts/scrape-socrates.mjs`, and `scripts/lib/socratesReplayHarness.mjs` already do,
and `src/cpp/tests/test_socrates.cpp` already has 5+ hardcoded golden pairs scraped
2026-03-10 with sub-second-precision TCA/range/speed/Pc reference values baked in.

**Practical capture recipe for A2.8b (politeness-respecting):**
1. One fetch of `sort-maxProb.csv` (and optionally `sort-minRange.csv`) — cached under
   `tests/data/.celestrak-cache/` (already wired via `celestrakFetchCache.mjs`).
2. Select a small, diverse N (existing scripts default to 5–20; the full CSV is
   reportedly ~120K rows across both sort orders — never bulk-fetch GP for all of them).
   Mix NLRV (rel. vel ≥ 50 m/s), LRV (10–50 m/s), and VLRV (<10 m/s, e.g. co-orbital
   constellation pairs) cases — the AMOS paper (Q5) shows tolerance requirements differ
   by an order of magnitude across these buckets, so the fixture set should stratify by
   them explicitly rather than just taking "top N by MAXPROB."
3. Fetch `data.php` once per selected pair, rate-limited (existing default 200 ms
   between requests — fine), cached to disk, **never retried past a non-200**, no
   proxy/Tor rotation ever.
4. Check the resulting `(GP pair, SOCRATES TCA/range/speed/MAX_PROB)` tuples into
   `src/cpp/tests/test_socrates.cpp`-style fixtures (or the JSON manifests under
   `tests/data/socrates_gp/`), each stamped with **capture wall-clock time** (since
   cadence isn't a fixed schedule — see Q1) so future re-captures are additive, not
   overwrites, building a growing regression corpus across different real SOCRATES
   runs over time.
5. Repeat this capture periodically (recommend: whenever the CA module's screening/TCA/
   Pc code changes materially, or at most monthly) — **from a host with real network
   egress**, not this environment.

**TraCSS/Aerospace IVV: capture strategy is different — it's a one-time, versioned
download, not a live poll.** There is exactly one dataset version today
(`20251009a`). "Reference window" here means: (a) download and extract the fixed
21.74 GB OCM tarball plus the two CSieve answer-key CSVs once, store them exactly where
`tests/data/README.md` already specifies (`tests/data/aerospace-archives/`,
`tests/data/aerospace-ivv/`), and (b) treat the whole `2025-01-01T12:00Z..2025-01-08T12:00Z`
window as one fixed, reusable regression fixture — there's no "capture cadence" to
manage, just an access-gate (Google account / OSC contact) to clear once. Because this
dataset is versioned (`20251009a` suggests future `..b`, `..c` releases are possible),
A2.8b's harness should key off the dataset version string, not assume it's evergreen.

## Q5 — Proposed parity tolerances for A2.8b

### 5a. Grounded in the AMOS 2025 paper's actual tool-to-tool results

This is real empirical data, not a guess: Aerospace validated **SpaceX's** operational
CS algorithm against CSieve over a full LEO constellation dataset. Final results
(their Table 9, both algorithms using an **identical 5 km spherical screening volume**
and identical inputs):

| Metric | Value | Comment |
|---|---|---|
| Events found by both | 263,633 | |
| Events found by CSieve only | 2 | miss distance ≈ 4.9999 km — a rounding artifact exactly at the 5 km boundary |
| Events found by SpaceX only | 4 | same rounding-boundary artifact |
| Max \|TCA diff\|, all events incl. LRV | 8.28 s | dominated by very-low-rel-velocity cases |
| Avg \|TCA diff\|, all events incl. LRV | 1.5 ms | |
| Max \|TCA diff\|, NLRV only (rel. vel ≥ 50 m/s) | 1.7 ms | |
| Avg \|TCA diff\|, NLRV only | 0.011 ms | |
| Max \|miss-distance diff\| | 6.8 cm | not correlated with relative velocity |
| Avg \|miss-distance diff\| | ~2.8 mm | consistent whether LRV included or not |

**Their own recommended TCA tolerance-by-velocity-regime (their Table 2, the number the
User's Guide explicitly points readers to):**

| Regime | Relative velocity | Suggested TCA tolerance |
|---|---|---|
| VLRV (very low) | < 10 m/s | ~10 s |
| LRV (low) | 10–50 m/s | ~0.01 s |
| NLRV (non-low) | ≥ 50 m/s | ~0.001 s |

Plus two hard component-level requirements from their Table 1:
- **Position at TCA: 1 m relative accuracy** (interpolation requirement).
- **Covariance at TCA: within 0.1 Bhattacharyya Distance** of the trusted tool.

Their own qualitative guidance for what counts as a "successful validation" (§4,
verbatim): *"For non-low relative velocity events, the two screeners should agree
nearly exactly on the events found, where any deviations may be attributed to slight
differences in the miss distance surrounding the screening volume threshold... For low
relative velocity events, more leeway is permitted... So long as the same events are
found with approximately similar times of closest approach, a validation of a CS
algorithm may be considered successful."*

### 5b. Recommended A2.8b tolerance table (synthesized)

| Axis | Against SOCRATES (live replay of `data.php` GP pairs, same-element comparison) | Against TraCSS/CSieve (OCM all-vs-all, same-element comparison) | Rationale |
|---|---|---|---|
| **Event-set recall** | ≥ 99% of SOCRATES-reported pairs in the sampled fixture set must reproduce a conjunction; 0 tolerance for silent drops on NLRV pairs | 100% of CSieve events for object-ID range 00005–62461 (TLE-catalog objects) at NLRV; ≥ 99.9% overall matching CSieve's own SpaceX-vs-CSieve empirical rate (263,633/263,637 ≈ 99.9985%) | Both sources' own validation reports treat near-100% NLRV recall as the bar; a handful of boundary-rounding misses (exactly at threshold) are expected and not failures |
| **Event-set precision (extra events)** | Same bound as recall — extras only tolerated within the same threshold-rounding band (< 1 m outside the 5 km / 10 km / SFSH boundary) | same | Matches the 2-vs-4 rounding artifacts Aerospace itself accepted |
| **TCA delta — NLRV (≥50 m/s)** | ≤ 1 ms (target), ≤ 10 ms hard fail bound | ≤ 1 ms (target), ≤ 10 ms hard fail bound | AMOS paper measured avg 0.01 ms, max 1.7 ms in a real passing tool |
| **TCA delta — LRV (10–50 m/s)** | ≤ 10 ms (target), ≤ 100 ms hard fail bound | same | AMOS Table 2 suggests ~0.01 s |
| **TCA delta — VLRV (<10 m/s)** | ≤ 10 s hard fail bound; success = "found the event at all," TCA precision explicitly de-emphasized | same | AMOS Table 2 / §4 explicit guidance — do not over-tighten this bucket |
| **Miss-distance delta** | ≤ 10 cm hard fail bound, ~mm-level target | same | AMOS measured max 6.8 cm / avg 2.8 mm between two independently-implemented, passing tools |
| **Position-at-TCA accuracy** | 1 m (component requirement, not just pairwise delta) | same | Direct from AMOS Table 1, Req 1.3 |
| **Covariance-at-TCA accuracy** | 0.1 Bhattacharyya Distance | same, if/when we emit full 6x6 covariance (see gap below) | Direct from AMOS Table 1, Req 1.4 |
| **Pc** | Advisory only: within 10x (order of magnitude) of SOCRATES `MAX_PROB`, since both use Alfano-max-Pc family | **Not gated at all** — TraCSS/CSieve uses a different Alfano variant and the source documents explicitly exclude Pc from CS validation | Explicit statements in both the User's Guide and AMOS 2025 paper |
| **Screening-volume boundary handling** | Any mismatch strictly at the 5 km/10 km threshold (±10 cm) is a known-acceptable rounding artifact, not a bug | same, plus SFSH asymmetric-reporting rule (A→B ≠ B→A) must be tested explicitly | Both artifacts document this exact behavior |

### 5c. What's explainable by catalog-epoch mismatch vs. propagator vs. Pc method

- **Catalog-epoch mismatch** (our OMM epoch ≠ SOCRATES's snapshot epoch, or ≠ TraCSS's
  1-Jan-2025 TLE epoch): this is the dominant, *expected* error source once we compare
  our own A2.7-synthesized catalog (not a replay of the reference's own GP elements) —
  SGP4 divergence grows roughly with propagation time from epoch, so a several-hour-old
  fit vs. a same-epoch fit can plausibly differ by 10s of meters to km-scale over a
  7-day window depending on drag regime. **This tolerance band is NOT covered by the
  AMOS numbers above**, which compare two tools given *identical* input elements. A2.8b
  needs a **separate, wider tolerance band** for "our synthesized catalog vs. reference"
  runs (Stage B, see harness recommendation below) — recommend deriving it empirically
  from the existing A2.4 OD-fit RMS gates (our fit vs. CelesTrak SupGP RMS) rather than
  guessing a number here.
- **Propagator differences**: not applicable for the TLE-catalog portion of either
  reference (both SOCRATES and TraCSS's 00005–62461 range use SGP4, matching our
  module). It **is** applicable to TraCSS's maneuvering/fictitious/heliocentric ranges,
  which were generated with high-fidelity numerical integration (Jacchia-Bowman-HASDM
  2009 density, luni-solar, SRP) — our SGP4-only module will show larger, *expected*
  divergence there; treat those object-ID ranges as "algorithmic correctness" tests
  (does the machinery handle the geometry at all), not "numeric parity" tests.
- **Pc method differences**: addressed above (Q3/5b) — bounded to order-of-magnitude
  against SOCRATES only, unbounded/advisory against TraCSS.
